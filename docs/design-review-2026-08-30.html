#69 technical chore design v2, after founder feedback

Leases, negotiation and a schema preflight for the shared local Supabase

Version 2. Three things changed from v1, all from your feedback: (1) using the database is not the problem, changing it is, so readers run concurrently and only modifiers have to ask; (2) every database user checks the schema it is about to run against, before it starts; (3) nothing here is a daemon, a queue or a scheduler, and the happy path costs one file write and one SQL query. Sections marked with the saffron bar are the changed ones.

1. The model: readers coexist, modifiers ask

Readers concurrent

Use the database as an application user. They never change its shape or restart it.

  • A Playwright run (api or ui), including the no-mistakes gate's test step
  • A human or agent in psql or the Studio, seeding a demo, poking at rows
  • The dev server (npm run dev)

Any number of readers at once. Each holds a read lease that says who, from where, since when, and how long they expect to need it.

Modifiers must ask

Change the database's shape or availability for everyone.

  • db:reset (drops everything)
  • db:start, db:stop, a Docker restart
  • migration up on a branch whose migrations differ
  • check:migration-against-tenant (destroys and rebuilds)

A modifier needs a write lease, which it can only take when no live read lease objects. If readers are active, it posts a request and they get a say.

2. How a modifier asks, and how readers answer

This is the part you asked for: a modifier tells the other agents what it wants and how long, and they can respond if they care.

The three answers a reader can give

AnswerCommandMeaning
oknpm run db:lease respond r-3f2 --okGo ahead now. I am done, or my run can be sacrificed (the agent re-runs it later).
need Nnpm run db:lease respond r-3f2 --need 4mWait; I need about four more minutes. Updates my lease's expected_until.
silencenothingThe modifier falls back to my lease's expected_until. A Playwright run cannot answer for itself, so its lease carries an honest estimate (measured: about 6 minutes for the full suite) and interruptible: false.

What the modifier does with the answers

  • Every live reader said ok (or every read lease is stale): takes the write lease, proceeds.
  • Someone needs time: prints who and until when. With --wait it polls until all read leases are gone or answered ok, then proceeds. Without, exits 75 (EX_TEMPFAIL) with the ETA so the calling agent can decide.
  • Silence past the grace window (default 20 s): same as "need time until expected_until". If expected_until has passed and the pid is still alive, the reader has overrun; the modifier says so and keeps waiting under --wait, or the human uses --force.
Readers never wait for anything except a write lease that is already active (a reset in progress). A new reader arriving during a reset is told "database is being reset by X, about 90 s left" and can --wait. That is the only case a reader is ever held.

Two scopes, from your note

Docker and the Supabase stack as a whole are a laptop-level resource: a Docker restart touches every project's containers. A schema change is project-level: another repo's database does not care that this one was reset. So the state dir has two levels and every lease and request carries a scope:

~/.local/state/dblease/
  _machine/                 scope: machine   (docker restart, "stop everything")
    leases/  requests/
  hybrid-donation/          scope: project   keyed by supabase project_id
    leases/  requests/  schema.json
  some-other-repo/          a second project, when one exists
  • A project-scope modifier (db:reset, db:migrate, db:start/db:stop for this project) consults only this project's read leases.
  • A machine-scope modifier (a Docker restart, or a future "stop all Supabase projects") consults every project's read leases, and posts its request in each project's requests/ so each project's readers are told through their own channel.
  • Readers always register under their project. A reader in another repo is invisible to this project's modifiers, which is the point.
The tool itself starts life in this repo (scripts/lib/db-lease.mjs), with the directory layout and JSON format designed for the two scopes from day one. Extracting it to a shared CLI under ~/.local/bin, next to treehouse and no-mistakes, is a later step for when a second repo needs it; nothing about the layout has to change then.

3. The schema preflight

Your second point: an agent should know whether the database's schema matches the checkout it is about to test, before it starts.

The version already exists in two places

In the repo: supabase/migrations/. The sorted list of filenames is the schema version of a checkout; each branch has its own.

In the database: supabase_migrations.schema_migrations, which the Supabase CLI maintains: one row per applied migration version.

So the preflight is one query compared with one directory listing. Nothing new has to be written or kept in sync, which is why I recommend against a separate committed version file: it would be a third copy that can drift from the other two.

Also written to the shared state dir

After every modifier run, the tool writes schema.json: the applied set, the branch and worktree that applied it, and when. That is the human-readable "what is the database currently built from" you asked for, visible in db:lease status without a query, and it is derived, so it cannot drift.

The one real risk of concurrent readers. GoTrue rate-limits sign-ins per IP. Two suites at once double the sign-in rate, and the auth backoff spec (members-auth-backoff.spec.ts) is timing-sensitive; it flaked once today on a cold stack. If two-suite runs prove flaky in practice, the fix is playwright test --exclusive (a write-style lease for one run), not a return to the global lock. Start permissive, tighten on evidence.

6. Testing

  • Unit (vitest, 100% of the two lib modules, temp dirs, fake pids): concurrent read leases; write refused by a live read; write granted when all replied ok; write granted when read is stale; need N extends the ETA; grace-window expiry; release only with matching token; classification of all four schema outcomes from fixture lists.
  • Process-level: spawn a hold child, run a modifier against the same temp state dir, assert it posts a request and exits 75 with the child's details; then respond --ok from a third process and assert it proceeds.
  • Playwright wiring: the full suite green under the new globalSetup/globalTeardown, lease file gone afterwards, plus a deliberate foreign run (a throwaway migration in a temp copy) asserting the preflight message.

7. Risks and limits

Consent is advisory for silent readers. A Playwright run cannot answer; its estimate stands in for it. If a run overruns badly, a modifier under --wait keeps waiting, and a human can --force. That is the right default for a shared resource.
Not a queue. Two modifiers waiting on the same readers race when the leases clear. Fine for one machine and a handful of sessions.
Wrong-pid takeover. A dead holder's pid reused by an unrelated process keeps a lease looking live until that process exits. Rare on macOS; release --force covers it.
Still not isolation. This coordinates access; it does not give two branches two databases. If genuine parallel schema work is ever needed, #69's per-worktree Supabase project option remains, and the leases stay useful as the default.

8. Sharing the pattern with other people (your question, second pass)

You are right, and I answered the wrong question. An npm package only reaches people whose project already uses npm. The way lavish, treehouse and no-mistakes are shared is the right model, and it is how CLI tools that carry a pattern are generally shared: one static binary per OS, an install one-liner, and a README that teaches the pattern, so a Python, Go or Rails project on Windows, Linux or a cloud runner can adopt it with no runtime to install.

The tool: dblease, a static binary

  • Own public repo, MIT. Built with the same toolchain as treehouse and no-mistakes, which are both Go binaries (go 1.25, checked on this machine): one self-contained executable, nothing to install first.
  • Releases on GitHub for macOS (arm64, x64), Linux (x64, arm64) and Windows (x64). Install: curl -fsSL …/install.sh | sh on macOS and Linux, irm …/install.ps1 | iex on Windows; a Homebrew tap and winget later if people ask.
  • Cross-platform details handled inside the binary: state dir (~/.local/state on macOS/Linux, %LOCALAPPDATA% on Windows), desktop notification (osascript, notify-send, Windows toast), pid liveness on each OS.
  • Language-agnostic: the schema probe is configured, not hard-coded. dblease.toml in the project root names the project id, the migrations directory, and the command that prints the database's applied versions. Supabase comes with a built-in probe; Prisma, Flyway, Alembic or plain SQL get a one-line command in the config.

The pattern: taught, not just implemented

  • The README explains the model in plain language: readers coexist, modifiers ask, silence is not consent, the four preflight outcomes, two scopes. Someone can read it and adopt the pattern by hand without the tool.
  • SKILL.md lives in the same repo: plain markdown any agent harness can load. Claude Code users install it with npx skills add sundeepdev/dblease; others copy the file. It teaches an agent when to run dblease status, how to answer a request, what exit 75 means.
  • dblease init writes the config and, when it detects the project type, the wiring: a Playwright globalSetup stub for Node projects, a conftest.py hook for pytest, a Makefile target otherwise. That is the "shell command that sets the pattern up" you asked for.
What this repo then contains. Almost nothing: dblease.toml, db:lease and db:migrate script entries that shell out to the binary, two tiny Playwright hook files that do the same, and the AGENTS.md rules. The project-template gets the same four things plus one line in its AGENTS.md, so every new project inherits the pattern. ~/.claude/CLAUDE.md gets one line under Workflow conventions pointing at the skill.
Cost, honestly. A Go binary with releases and an installer is a bigger first step than scripts in this repo: roughly the shape of treehouse. By your rule on implementation cost that is the right call, because the other shapes reach fewer people or drift. The build order stays: tab 2 builds dblease first (binary, tests, README, SKILL.md, installer), then wires this repo for #69 and the template.

8a. Superseded first answer (kept so the thread reads in order)

You asked whether this should be a skill or a design that other laptops, other people and cloud setups can use. My answer: both, in three layers, because each layer has a different audience and a different reason to change.

1. The tool: dblease

Its own repo, ~/ws/dblease (sundeepdev/dblease), the same shape as treehouse. Pure Node, zero dependencies, published as an npm package.

A project consumes it as a devDependency, so npm ci on any laptop or cloud runner installs it; no global install to forget. Humans may also install it globally for dblease status from anywhere.

Per-project config lives in the repo (dblease.config.json): project id, migrations dir, DB URL, purposes and their estimates. The two-scope layout is built in.

2. The skill: ~/.claude/skills/dblease/

Teaches an agent when and how: preflight before any database use, read status, answer requests, hold for ad-hoc work, what exit 75 means. Loads only when the task touches a shared database, per your memory discipline (conditional knowledge goes in a skill, not CLAUDE.md).

Managed with npx skills, so it syncs to another laptop and can be shared with others. The same SKILL.md ships inside the tool's repo, so anyone who installs the package can install the skill.

3. Pointers, one line each

  • ~/.claude/CLAUDE.md, Workflow conventions: "shared local databases are coordinated through dblease; see the skill".
  • hybrid-donation/AGENTS.md: #69's discipline rules replaced by "readers run, modifiers ask" and the four preflight outcomes; firstmate crew rules shrink accordingly.
  • ~/ws/project-template: AGENTS.md line, the devDependency, the db:lease script entries and the Playwright hook stubs, so every new project inherits it.
  • firstmate dispatch brief: readers and modifiers named, so a crew never needs the old serial rule.
Why not "just a skill". A skill can only tell an agent what to do; it cannot make the gate's Sonnet, a Playwright globalSetup, or a CI runner do anything. The behaviour has to live in code the scripts call. And why not "just in this repo": the second project on this laptop would either copy it (drift) or share nothing (the machine-scope lease would see only one project). A package is the one shape that works on this laptop, on another laptop, in the cloud, and for someone else.
Sequencing change. Tab 2 builds the dblease repo first (package, tests, skill), then wires hybrid-donation for #69 and the template. That is more work than v2's "scripts in this repo", and it is the better design by your own rule on implementation cost.
