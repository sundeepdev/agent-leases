0. Answers to your eight comments, and what each changes

0.1 Rule 2: "if the parent is consulted, the children must be consulted too"

Agreed, and that is what Rule 2 already says: a modifier of T consults T and every descendant (the children, grandchildren, and so on). "Never an ancestor" means the other direction only: a db:reset does not ask the dev server sitting on supabase above it. The wording on the diagram was the problem, not the rule.

Your reframing as a dependency graph is better, and I propose adopting it. Each tool declares what it depends on (db depends on supabase, which depends on docker), the graph is a DAG rather than a strict tree (a future tool can depend on two things, say a device and a network service), and the one rule becomes: a modifier of X consults the readers of X and of everything that depends on X, transitively. Each tool adapter also declares its actions, tagged reader or modifier, as you suggest. Same behaviour as the tree in every case in the table; strictly more expressive; and the word "dependency" says why the rule is what it is. changes LLD 2

0.2 When do readers wait by default?

Only in one situation: a reader is starting while a write lease is already active on its tool or on something its tool depends on, for example Playwright starting while a db:reset is halfway through. Then it waits, with a progress line, up to five minutes, instead of failing against a half-built database. During a normal run readers never wait for anything, and they are never interrupted; the pattern's whole point is that a running reader is left alone. no change

0.3 "local-db.mjs is not wrapped", in plain words

scripts/lib/local-db.mjs is a shared library, not a command. It holds the delicate three-step reset that seeds the donor-encryption key at the right moment (reviewed once under ADR-0011; a mistake there makes donor tax IDs unrecoverable). Commands such as npm run db:reset and npm run db:start call into it.

The choice is where the lease is taken. Option A: inside the library, so every caller gets it for free. Option B: in each command script, just before it calls the library. The LLD picks B. Example: npm run db:reset runs db-reset-local.mjs, which takes the write lease on db, then calls the library exactly as today, then releases. Two reasons: the library's encryption-key code stays byte-for-byte as reviewed, and a script that already holds a lease can never accidentally take a second one through the library. Cost: the four entry scripts each get the same three lines. no change

0.4 Should the state dir have subdirectories by tool, project or graph?

It does, by tool: ~/.local/state/agent-leases/<tool>/{leases,requests,state.json}, one directory per node, and because node ids are type:instance (db:hybrid-donation), "per project" falls out of the naming without a second level. The graph itself is not encoded as directory nesting, because a DAG cannot be a directory tree; it is declared by the adapters and written once as graph.json beside the tool directories so status can draw it and a second repo can see what this one declared. adds graph.json to LLD 3

0.5 Interruptible: a way to mark something important or urgent; environment-based configuration

Agreed, two additions. (a) A request carries urgency: normal | urgent and a lease carries importance: normal | high; status and every message show them, and an urgent request is what a human reaches for when a reset cannot wait, while a high importance lease is one a modifier should never treat as interruptible whatever its flag says. (b) An environment profile (LEASE_PROFILE=dev|shared|prod-like, defaults in a small config file) that sets the defaults: in dev, dev-server leases are interruptible and the grace window is 20 s; in prod-like, nothing is interruptible by default and the grace is longer. This slice implements the fields and the dev profile only; the others are documented as the shape. changes LLD 3 and 4; new upstream finding

Added from your follow-up: every request carries a short free-text message from the modifier ("resetting to apply the #87 correction migrations", "restarting Docker to clear a hung container"), shown in the banner, in status and in the reader's refusal text, so a running agent can judge whether its own work is important enough to answer need or is itself dependent on the change and should answer ok. The message is required for urgent requests and optional otherwise. changes LLD 3.3

0.6 The fifth outcome, unknown, in plain words

Before Playwright runs, the preflight asks Postgres "which migrations have you applied?" and compares with the checkout. To ask, it needs the pg library from node_modules. The no-mistakes gate runs in a throwaway worktree that often has no node_modules, so the question cannot be asked at all. Two choices: fail the run ("I could not check"), which blocks the gate for a reason that has nothing to do with the branch, or say "could not check, continuing" once and run the suite. The LLD picks the second and calls that outcome unknown. Relevance to the pattern: a coordination layer must never be the reason a run fails, except by a finding of its own; a probe that cannot run is not a finding. no change

0.7 Queue modifiers like a merge queue, and batch pending changes

Partly agree, and the part I agree with is cheap. Ordering: requests are timestamped files, so "first posted goes first" costs nothing and needs no daemon; a second modifier waits its turn under --wait instead of being refused. Adopt. Take the latest state when your turn comes: adopt as "re-run the preflight at your turn and skip if already satisfied"; a db:migrate queued behind another finds nothing left to apply and exits clean. Batching several pending changes into one: only safe when they are the same kind. Two db:migrate requests coalesce naturally (the second is a no-op). Two db:reset requests from different branches cannot be merged: they want different schemas, and the second must still run after the first, which is the case that started this issue. So: FIFO queue, re-check at your turn, coalesce identical actions, never merge distinct resets. changes LLD 4.3 and case 16 (refuse becomes wait-in-order)

Refined from your follow-up: coalescing is per tool, and it is decided by the re-check rather than by the action's name. Two db:reset requests on db:hybrid-donation merge when the first reset leaves the database in a state the second requester's checkout accepts (same branch, or same migration set): its re-check says match and it exits clean without resetting again. If the two requesters are on different branches, the second's re-check says foreign and it still resets, which is correct because the two genuinely want different schemas. Requests on different tools (db:hybrid-donation versus db:other-repo) are never compared. consistent with 0.7

0.8 Interfaces with OS, harness and A2A adapters

Agreed, and it is the right way to make the pattern adoptable. The LLD will name five interfaces, each with this slice's one implementation: StateStore (a directory of JSON files), Liveness (process.kill(pid, 0)), ToolAdapter (declares dependencies, actions, estimates), Probe (returns the two sorted lists, or unknown), and Notifier. For Notifier this slice ships only "the status command" (desktop banners are cut), but the interface is where a harness adapter plugs in: Claude Code's cross-session messaging, an MCP notification, or an A2A task message are each one adapter. To your question, no harness or agent platform I know of has a shared-resource lease primitive: A2A negotiates tasks between agents, MCP exposes tools, and neither says anything about two agents sharing one database. That gap is the reason this repo exists. changes LLD 1 and 15; new upstream finding

0.10 "If the database is the same, how can two resets want different schemas?" You are right, and it changes the preflight

They cannot, not on one shared database. Two branches that each need the database rebuilt to their migration set are not sharing it; they are taking turns destroying each other's state, and my 0.7 wording ("the second still resets, correctly") described that ping-pong as if it were fine. Your principle is the right one: a shared tool has one state, the same for every agent, and agents adapt to it rather than reset it to look like their own checkout.

What that means for the database, concretely: the shared state should converge to the union of every live branch's migrations. Migrations here are append-only and version-ordered (check:migrations forbids editing a merged one), so applying branch A's and branch B's migrations to one database is normal, and it is exactly what main will look like after both merge. The preflight outcomes become:

Database vs my checkoutOutcomeWhat happens
Same setmatchproceed
Database lacks some of minebehindstop; db:migrate -- --wait applies only the missing ones, additive, negotiated. Never a reset.
Database has extras from another branch, and all of mine are appliedaheadwarn and proceed, naming the extra migrations and the branch that applied them, so a test that fails because of them is attributable. This replaces the old "foreign stops" for the superset case.
Database lacks some of mine and has extrasbehind + aheadthe same db:migrate; afterwards it is ahead, and proceeds with the warning
db:migrate itself fails (two branches created conflicting migrations)conflictthe one genuine case for db:reset, negotiated and serial, and it means those two branches cannot share this database until one merges. The message says so.
Empty or absent / probe cannot runnone / unknownas before

Consequences: db:reset stops being the reflex and becomes the exception; the merge-queue question in 0.7 mostly dissolves, because queued db:migrate requests coalesce perfectly (each applies only what is still missing) and queued resets are rare; and the gate's usual outcome (behind) resolves additively without touching anyone else's work. The risk, stated: a superset can make one branch's tests fail when another branch's migration changes behaviour the first asserts (this repo has one such branch today, #47's grant-stripping migration). The warning names the culprit; LEASE_STRICT_SCHEMA=1 restores "any difference stops" for whoever wants it. This supersedes Q3 as asked: foreign no longer exists as an outcome, so the question becomes whether conflict may fail the gate, and the answer is yes. changes LLD 5, 6.4, cases 3, 4 and 16; the strongest upstream finding so far

0.9 The amendments, in one decision

  1. Dependency graph (DAG, declared by adapters, actions tagged reader/modifier, graph.json) replaces the tree in wording; behaviour identical for every case in section 10.
  2. The shared database converges to the union of live branches (0.10): behind migrates additively, ahead warns and proceeds, reset only on conflict; decided separately in 0.10.
  3. Modifiers queue FIFO by request time and re-check at their turn; coalescing is per tool and decided by that re-check (a second reset on the same database exits clean when the first already satisfied it, and still runs when it did not); different tools are never compared. Case 16 changes from "refuse" to "wait in order".
  4. Requests carry urgency and a short free-text message (required when urgent); leases carry importance; an environment profile sets defaults, with only dev implemented now.
  5. Five named interfaces with one implementation each; Notifier ships as status-only in this slice.

2. Why the tree beats the two flat scopes you approved

SituationTwo flat scopesThree tools in a tree
db:reset while npm run dev runsThe dev server is a project reader; it cannot answer, so the reset waits out its estimate or is forcedThe dev server is on supabase, an ancestor: never asked. The reset proceeds at once, correctly
npm run dev starts during a db:resetHeld for the whole resetThe write lease is on a descendant; Vite starts immediately
db:stop while Playwright runsAsks Playwright. CorrectAsks Playwright, by the same one rule. Correct
Restart only this project's containersNot expressiblesupabase:hybrid-donation is its own node
A Docker restartA second, special-cased traversal into every project directoryThe docker node's descendants; the same traversal as everything else
A future device, emulator, staging environmentA third scope, then a fourthA new node. No new concept

The gain is not more features: one relation (ancestor / descendant) replaces two special cases, and it buys a distinction the flat model cannot express: changing what is in the database is a smaller act than taking the database away.

What it costs (HLD 2.3). A reader registered at the wrong level is silently under-protected (mitigated: callers never pass a tool id, the adapters own registration). Node ids become a machine-global namespace, type:instance, to agree upstream before a second repo adopts. About thirty lines of graph walking. And the middle node is empty unless npm run dev is wrapped, which is founder question 1 below.

3. Where the LLD departs from the approved design

The lead's summary flags these as contradictions of the 2026-08-30 text. None reverses one of your seven decisions; each closes a gap. Flagged ones change something you approved by name.

Flagged An exhausted estimate never authorises a modifier

The approved text can be read as "proceed when the ETA passes". That would destroy exactly the overrunning suite the pattern exists to protect. A live, non-interruptible reader blocks until it releases, answers ok, or is forced. The estimate is for planning and the message only.

Flagged Readers wait by default (up to 5 min); modifiers do not

Approved text gave both sides an opt-in --wait. A test run that fails rather than waiting out a 90 s reset is a support request; a blocked modifier still exits 75 at once so an agent can do something else.

Flagged scripts/lib/local-db.mjs is not wrapped

Leases live in the entry scripts instead, so the donor-crypto Vault split (ADR-0011) stays byte-identical and no caller can double-acquire. The new db:migrate re-establishes that invariant explicitly at statement level; the lead calls it the single riskiest line in the slice.

Flagged State dir is ~/.local/state/agent-leases, not dblease

Two of the three tools are not databases, and it matches the upstream repo name. Cheap now, annoying later.

interruptible: true is consent given in advance

The approved design defined the field and never said what a modifier does with it. Now: an interruptible reader (the dev server) is notified and not waited for, and can withdraw with respond --need.

A fifth preflight outcome: unknown

When import('pg') fails in a worktree with no node_modules (the gate's norm), warn and proceed. Without it the layer fails closed in the one environment it was built to protect.

Two modifiers refuse rather than race

A write lease blocks another write lease anywhere on the same ancestor/descendant path. One extra check removes a limit the upstream README simply accepts.

Fail closed on an unreadable lease; requests die with their poster

Atomic writes make partial reads impossible, so an unparseable file is corruption and blocks (cleared with release --force). A request is removed when its poster exits, so status never fills with questions nobody is asking.

7. How it is verified

No BDD layer (no product surface). Unit tests against temp state dirs and fake pids at 100% of scripts/lib/leases/**; process-level tests that spawn real hold children and a real modifier (the only layer that proves one process being right about another), including an assertion that git status --porcelain is empty after a full cycle; and a scripted manual proof against the real Playwright suite with a deliberately foreign database. The first two layers need no Docker or Postgres.
